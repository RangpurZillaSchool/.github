# Rangpur Zilla School — Open Source Organization

> **An organization created by Rangpur Zilla School students. Not affiliated with Rangpur Zilla School teachers or the Government of Bangladesh.**

**GitHub Organization:** `RangpurZillaSchool`
**Central Repository:** `.github`
**Current Organization Owners:** `TarangoHasan`, `Tanzeem`

---

# 1. Purpose

This organization exists to allow students and trusted contributors to build, publish, maintain, and collaborate on open-source software, educational tools, experiments, and other useful projects.

The organization is intended to be:

* Open-source
* Community-friendly
* Student-led
* Collaborative
* Educational
* Transparent
* Safe to contribute to
* Focused on building useful software rather than personal ownership

The organization may contain multiple independent projects. Each project may have its own roadmap, license, contribution rules, maintainers, and technical architecture.

---

# 2. Organization Philosophy

The organization is primarily a place for **building things together**.

Personal ownership, personal profit, or personal control should not be the main purpose of an organization project.

Contributors should receive appropriate recognition for their work through:

* Git history
* Pull requests
* Issues
* Project documentation
* Contributor lists
* Release notes
* Other appropriate project records

However, contribution credit should not automatically be interpreted as personal ownership of the entire project.

---

# 3. Public Contributions

Public repositories under this organization may accept contributions from anyone on GitHub unless a repository explicitly states otherwise.

A person may contribute by:

* Creating issues
* Joining discussions
* Forking repositories
* Creating branches
* Creating pull requests
* Fixing bugs
* Adding features
* Improving documentation
* Improving UI/UX
* Adding tests
* Improving accessibility
* Improving educational content
* Reporting security problems
* Suggesting improvements
* Helping with project research

Public contribution does not require the contributor to become an organization member.

The organization may accept, reject, modify, or request changes to any contribution.

---

# 4. Organization Membership

Organization membership is managed by the organization owners.

Membership may be given to people whom the owners trust and believe can responsibly participate in the organization.

Membership may be granted based on factors such as:

* Trust
* Contribution
* Technical ability
* Project involvement
* Reliability
* Collaboration
* Community behavior
* Existing relationship with the organization

There is no requirement that every public contributor become an organization member.

Being an organization member does not automatically give permission to:

* Delete repositories
* Transfer repositories
* Change organization ownership
* Change organization-wide security settings
* Modify another project without permission
* Access private information
* Access secrets
* Perform destructive administrative actions

Permissions should be granted according to actual responsibility.

Owner access should primarily be treated as a **responsibility**, not as personal ownership of every project.

# 6. Two-Owner Protection Rule

The organization should maintain at least two trusted owners whenever practical.

Major organization-level actions should require the agreement of both current owners.

This includes, but is not limited to:

* Transferring a repository
* Permanently deleting a repository
* Changing ownership of an important project
* Adding or removing an organization owner
* Changing important organization-wide security settings
* Permanently changing the organization's identity
* Making major changes that could materially damage the organization
* Giving away important organization assets
* Releasing private information
* Taking actions that could permanently remove project access

The purpose of this rule is **risk protection and continuity**, not to create unnecessary bureaucracy.

---

# 7. Repository Ownership

Repositories created under the organization are organization repositories.

They should not be treated as the personal repository of one member.

A member must not intentionally move an organization repository to:

* Their personal account
* Another personal account
* Another organization
* Another company
* Another person
* Another entity

without the required approval under the owner rules.

Repositories should remain under the organization unless a documented and approved reason exists.

---

# 8. Repository Transfer Rule

**Repository transfer is not an ordinary operation.**

A repository must not be transferred without:

1. A clear reason
2. Discussion between the organization owners
3. Approval from both owners
4. A documented record of the decision

Where technically possible, GitHub organization settings should restrict repository transfer and deletion permissions appropriately.

The organization should prefer keeping projects under its own GitHub organization.

---

# 9. Repository Deletion Rule

Permanent repository deletion should be avoided.

When a project is no longer active, the preferred action is:

> **Archive instead of delete.**

A repository should only be permanently deleted when there is a strong reason, such as:

* Severe security risk
* Legal requirement
* Accidental repository creation
* Duplicate repository
* Irrecoverable repository problem
* Another documented exceptional circumstance

Permanent deletion should normally require approval from both organization owners.

Before deletion, an appropriate backup or archival copy should be considered where practical.

---

# 10. Repository Visibility

Changing a project's visibility can have major consequences.

Changing:

* Public → Private
* Private → Public

should be considered a significant project decision.

Public projects should not be made private merely to remove community access without a reasonable reason and appropriate approval.

Private repositories must still follow all applicable security and access rules.

---

# 11. Repository Rules

Each important repository should define its own technical rules.

A repository may contain:

* `README.md`
* `CONTRIBUTING.md`
* `LICENSE`
* `CODE_OF_CONDUCT.md`
* `SECURITY.md`
* `ROADMAP.md`
* Project-specific governance documents
* Issue templates
* Pull request templates
* Code ownership rules

The central `.github` repository contains organization-wide rules, while individual repositories may add more specific rules.

When a project-specific rule conflicts with an organization-wide rule, the more restrictive security or ownership rule should normally take priority.

---

# 12. Pull Requests

Public contributors should generally contribute through:

```text
Fork
  ↓
Branch
  ↓
Changes
  ↓
Pull Request
  ↓
Review
  ↓
Approval
  ↓
Merge
```

Direct write access should only be given when necessary.

Pull requests should ideally:

* Have a clear purpose
* Explain what changed
* Explain why it changed
* Avoid unrelated changes
* Preserve existing functionality
* Include tests where appropriate
* Avoid introducing security problems
* Avoid exposing secrets
* Avoid exposing private information

Maintainers may request changes before merging.

A pull request may be closed if it is:

* Unsafe
* Malicious
* Unmaintainable
* Unrelated
* Repetitive
* Incompatible with the project
* Missing necessary information

---

# 13. Major Project Changes

A major project decision should normally be discussed before implementation.

Examples include:

* Major architecture changes
* Database redesign
* Replacing the primary framework
* Removing a major feature
* Adding a major system
* Changing the project's identity
* Changing the project's license
* Major privacy changes
* Major security changes
* Changing the intended audience
* Transferring project responsibility
* Abandoning the project

The purpose is to protect the project from accidental or harmful decisions.

---

# 14. Community Proposals and Voting

Projects may use GitHub Issues or Discussions for major proposals.

A proposal should explain:

* The problem
* The proposed solution
* Alternatives
* Advantages
* Disadvantages
* Technical impact
* Security impact
* Privacy impact
* Maintenance impact

A project may choose to use community voting for major product-direction decisions.

Voting rules must be documented by the project before the voting process begins.

Community voting may be:

* Advisory
* Binding
* Limited to maintainers
* Open to contributors
* Open to broader community participants

The applicable project must clearly define which model it uses.

---

# 15. Maintainers

A project may have maintainers who are responsible for keeping the repository healthy.

Maintainers may:

* Review pull requests
* Merge approved changes
* Manage issues
* Label issues
* Manage releases
* Review project documentation
* Perform normal maintenance
* Help contributors
* Fix bugs
* Improve code quality

Maintainers are **not automatically organization owners**.

A maintainer's permissions should match their responsibilities.

---

# 16. Owner vs Maintainer

These roles are different.

### Organization Owner

Responsible for organization-level administration and protection.

### Repository Maintainer

Responsible for maintaining a particular repository.

### Contributor

Contributes code, documentation, design, testing, research, educational material, or other work.

### Public Contributor

A contributor who may not be an organization member but contributes through public GitHub mechanisms.

---

# 17. Security

The following must never be publicly exposed:

* Passwords
* API keys
* Access tokens
* Private database credentials
* Service-account credentials
* Private student data
* Private messages
* Authentication secrets
* Private school information
* Other sensitive credentials

Secrets must be stored using appropriate secret-management mechanisms.

If a secret is accidentally published:

1. Remove the exposure where possible
2. Revoke or rotate the credential
3. Assess the impact
4. Correct the repository
5. Document the incident when appropriate

---

# 18. Student Privacy

Projects intended for students must take privacy seriously.

Projects should avoid unnecessarily collecting:

* Personal contact information
* Sensitive personal information
* Passwords outside proper authentication systems
* Private conversations
* Unnecessary academic information

Public repositories should use fictional or anonymized data for examples.

Student information should never be committed to GitHub.

---

# 19. Educational Content

Educational information should be reviewed before being treated as authoritative project content.

AI-generated content should not automatically be considered correct.

Important educational material should be:

* Reviewed
* Tested
* Corrected
* Properly sourced where appropriate

AI may assist with:

* Drafting
* Summaries
* Examples
* Question generation
* Explanations

but important educational content should have appropriate human verification.

---

# 20. Licensing

Each public project must clearly state its license.

The project's license should be included in its repository.

The organization may use open-source licenses such as:

* MIT
* Apache-2.0
* GPL
* AGPL
* Other appropriate licenses

The exact license belongs to the individual project unless an organization-wide standard is established.

Contributors must not intentionally submit copyrighted material that they do not have permission to redistribute.
